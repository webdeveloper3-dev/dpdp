1.1 The Business Need: Why Service-Based IT Companies Need a Generalized DPDP Engine
------------------------------------------------------------------------------------
As a service-based software development company building applications (ERPs, CRMs, FinTech apps, 
EdTech portals, Healthcare systems, E-Commerce, mobile apps) for various enterprise clients, your clients 
face severe statutory penalties under the Digital Personal Data Protection (DPDP) Act 2023:
- Up to INR 250 Crores for failure to implement reasonable security safeguards preventing data breaches.
- Up to INR 200 Crores for failure to notify the Data Protection Board of India (DPBI) and affected users.
- Up to INR 200 Crores for violation of special duties regarding Children's data (<18 years).
- Up to INR 150 Crores for failure to fulfill Data Principal Rights and Notice/Consent mandates.

Instead of writing custom, bespoke compliance logic for every client from scratch, building a 
**Generalized, Headless DPDP Compliance Engine & Reusable SDK** gives your company:
1. Standardized Reusable IP: One core engine deployed as a library, microservice, or Dockerized sidecar.
2. Faster Go-To-Market: Client applications achieve 100% DPDP compliance in days rather than months.
3. Universal Compatibility: Works across Node.js/Express, Python/Django/FastAPI, Java/Spring, and PHP.
4. Seamless Auditability: Automated translation of the 13 statutory governance forms into live system tables.

1.2 Core Legal Principles of DPDP Act 2023
------------------------------------------
The framework operationalizes the seven foundational principles of the Act:
1. Principle of Consent & Lawful Processing (Section 4 & 6): Personal data can only be processed with 
   free, informed, specific, unconditional, and unambiguous consent, accompanied by an itemized notice.
2. Principle of Purpose Limitation (Section 5 & 6): Data collected for Purpose A cannot be used for 
   Purpose B without obtaining fresh, explicit consent.
3. Principle of Data Minimization (Section 6(1)): Only collect personal data strictly necessary for the stated purpose.
4. Principle of Accuracy (Section 8(3)): The Data Fiduciary must ensure personal data is complete, accurate, 
   and consistently updated.
5. Principle of Storage Limitation (Section 8(7)): Data must be erased as soon as the purpose is served 
   or when consent is withdrawn, unless statutory retention is required.
6. Principle of Integrity & Confidentiality (Section 8(5)): Mandatory reasonable technical and organizational 
   safeguards (encryption, access controls, pseudonymization).
7. Principle of Accountability (Section 8): Maintain verifiable RoPA, audit logs, and grievance mechanisms.

2.2 Component Breakdown
-----------------------
1. Headless DPDP Core:
   - Contains business logic for Notice, Consent, Rights, RoPA, Encryption, and Grievance workflows.
   - Decoupled from any particular UI framework.
2. Backend Interceptor SDK (`@service-co/dpdp-engine`):
   - Express/Koa/NestJS/FastAPI middleware that intercepts incoming requests and outgoing responses.
   - Verifies active valid consent before controller execution.
   - Automatically masks PII data in responses according to role permissions.
3. Self-Service Data Principal Privacy Center (Web/Mobile Widget):
   - An embeddable React/Vue/HTML component for end-users to view active consents, withdraw consent, 
     download personal data summaries (DSR Access), and raise grievance tickets.
4. DPO / Admin Compliance Portal:
   - Enterprise dashboard for the client's Data Protection Officer (DPO) and compliance officers 
     to maintain RoPA forms 01-13, review DSR requests, handle grievances, and oversee breach drills.

2.3 Multi-Tenant / Multi-Client Architecture Pattern
----------------------------------------------------
For a service company managing dozens of client projects, the DPDP engine supports two deployment modes:
- Mode A (Embedded Module): Deployed directly inside the client's existing backend (same DB or schema).
- Mode B (Centralized Privacy-as-a-Service Microservice): A shared multi-tenant DPDP server hosting 
  compliance for multiple client projects, partitioned by `tenant_id` / `client_id` with separate encryption keys.

3.1 Master Catalog & RoPA Registry (Forms 01 - 04, 06)
------------------------------------------------------
```sql
-- Form 01: Departments and Business Functions
CREATE TABLE dpdp_departments (
    tenant_id VARCHAR(64) NOT NULL,
    department_id VARCHAR(32) NOT NULL, -- e.g. DEP-01, DEP-02
    department_name VARCHAR(255) NOT NULL,
    department_head_name VARCHAR(255),
    department_head_email VARCHAR(255),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (tenant_id, department_id)
);

-- Form 01: Business Processes (PRO ID)
CREATE TABLE dpdp_business_processes (
    tenant_id VARCHAR(64) NOT NULL,
    process_id VARCHAR(32) NOT NULL, -- e.g. PRO-01, PRO-02
    department_id VARCHAR(32) NOT NULL,
    process_name VARCHAR(255) NOT NULL,
    process_description TEXT,
    process_owner_name VARCHAR(255),
    process_owner_email VARCHAR(255),
    is_active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (tenant_id, process_id),
    FOREIGN KEY (tenant_id, department_id) REFERENCES dpdp_departments(tenant_id, department_id)
);

-- Form 03: Applications and Software Inventory (APP ID)
CREATE TABLE dpdp_applications (
    tenant_id VARCHAR(64) NOT NULL,
    app_id VARCHAR(32) NOT NULL, -- e.g. APP-01
    app_name VARCHAR(255) NOT NULL,
    app_type ENUM('WEB_APP', 'MOBILE_APP', 'DATABASE', 'SPREADSHEET', 'THIRD_PARTY_SAAS', 'LEGACY') NOT NULL,
    hosting_type ENUM('ON_PREMISE', 'CLOUD_INDIA', 'CLOUD_FOREIGN', 'HYBRID') NOT NULL,
    vendor_name VARCHAR(255),
    system_owner_name VARCHAR(255),
    data_backup_frequency VARCHAR(100),
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (tenant_id, app_id)
);

-- Form 04: Data Storage Locations (STR ID / REC ID)
CREATE TABLE dpdp_storage_locations (
    tenant_id VARCHAR(64) NOT NULL,
    storage_id VARCHAR(32) NOT NULL, -- e.g. STR-01 (Digital) or REC-01 (Physical)
    storage_type ENUM('SQL_DATABASE', 'NOSQL', 'OBJECT_STORAGE', 'FILE_SERVER', 'PHYSICAL_ARCHIVE') NOT NULL,
    storage_name VARCHAR(255) NOT NULL,
    cloud_provider VARCHAR(100), -- AWS, Azure, GCP, Local Data Center
    geographic_location VARCHAR(100) DEFAULT 'India',
    encryption_at_rest ENUM('AES_256', 'KMS_MANAGED', 'NONE') NOT NULL,
    access_protocol VARCHAR(100),
    is_cross_border BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (tenant_id, storage_id)
);

-- Form 06: Data Principal Categories (DPR ID)
CREATE TABLE dpdp_principal_categories (
    tenant_id VARCHAR(64) NOT NULL,
    category_id VARCHAR(32) NOT NULL, -- e.g. DPR-01 (Employee), DPR-02 (Customer), DPR-03 (Minor)
    category_name VARCHAR(150) NOT NULL,
    description TEXT,
    is_minor_category BOOLEAN DEFAULT FALSE, -- Requires Section 9 Parental Consent
    is_disabled_category BOOLEAN DEFAULT FALSE, -- Requires Section 9 Legal Guardian Consent
    approx_records_count INT DEFAULT 0,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (tenant_id, category_id)
);

-- Form 02: Personal Data Inventory Catalog & Risk Classification
CREATE TABLE dpdp_data_catalog (
    tenant_id VARCHAR(64) NOT NULL,
    item_id VARCHAR(32) NOT NULL, -- e.g. PII-01, PII-02
    process_id VARCHAR(32) NOT NULL,
    app_id VARCHAR(32) NOT NULL,
    storage_id VARCHAR(32) NOT NULL,
    category_id VARCHAR(32) NOT NULL,
    data_element_name VARCHAR(150) NOT NULL, -- e.g. Aadhaar, Mobile, Salary, Biometric Photo
    classification_level ENUM('CRITICAL', 'HIGH', 'MEDIUM', 'LOW') NOT NULL,
    storage_format ENUM('ENCRYPTED_TEXT', 'CLEAR_TEXT', 'HASHED', 'BINARY_BLOB', 'PHYSICAL_PAPER') NOT NULL,
    is_mandatory_for_service BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (tenant_id, item_id),
    FOREIGN KEY (tenant_id, process_id) REFERENCES dpdp_business_processes(tenant_id, process_id),
    FOREIGN KEY (tenant_id, app_id) REFERENCES dpdp_applications(tenant_id, app_id),
    FOREIGN KEY (tenant_id, storage_id) REFERENCES dpdp_storage_locations(tenant_id, storage_id),
    FOREIGN KEY (tenant_id, category_id) REFERENCES dpdp_principal_categories(tenant_id, category_id)
);
```

3.3 Notice & Dynamic Consent Artifact Registry (Form 13)
--------------------------------------------------------
```sql
-- Form 13: Privacy Notices (NOT ID)
CREATE TABLE dpdp_notices (
    tenant_id VARCHAR(64) NOT NULL,
    notice_id VARCHAR(32) NOT NULL, -- e.g. NOT-01
    version_tag VARCHAR(20) NOT NULL, -- e.g. 'v1.0.0', 'v2.1.0'
    language_code VARCHAR(10) DEFAULT 'en', -- e.g. 'en', 'hi', 'mr', 'ta', 'te' (22 Scheduled Languages)

    PRIMARY KEY (tenant_id, notice_id, version_tag, language_code)
);

-- Dynamic Immutable Consent Records (CON ID - Verifiable Audit Trail)
CREATE TABLE dpdp_consent_records (
    consent_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    tenant_id VARCHAR(64) NOT NULL,
    principal_id VARCHAR(128) NOT NULL, -- Unique identifier of Data Principal (User/Employee/Customer)
    notice_id VARCHAR(32) NOT NULL,
    notice_version VARCHAR(20) NOT NULL,
    language_code VARCHAR(10) DEFAULT 'en',
    consent_status ENUM('GIVEN', 'WITHDRAWN', 'EXPIRED', 'PAUSED') NOT NULL DEFAULT 'GIVEN',
    ip_address VARCHAR(45) NOT NULL,
    user_agent TEXT NOT NULL,
    consent_signature_hash VARCHAR(64) NOT NULL, -- SHA-256 (principal_id + notice_version + timestamp + salt)
    is_minor BOOLEAN DEFAULT FALSE,
    guardian_principal_id VARCHAR(128) NULL, -- Required if is_minor is TRUE (Section 9)
    guardian_verification_proof VARCHAR(255) NULL,
    given_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    withdrawn_at TIMESTAMP NULL,
    INDEX idx_principal (tenant_id, principal_id),
    INDEX idx_status (tenant_id, consent_status)
);

-- Granular Purpose-Wise Consent Itemization
CREATE TABLE dpdp_consent_items (
    item_id BIGINT AUTO_INCREMENT PRIMARY KEY,
    consent_id BIGINT NOT NULL,
    purpose_id VARCHAR(32) NOT NULL,
    is_granted BOOLEAN NOT NULL DEFAULT FALSE,
    granted_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (consent_id) REFERENCES dpdp_consent_records(consent_id) ON DELETE CASCADE
);
```

5. SECURITY, ENCRYPTION & DATA PROTECTION SUBSYSTEM (SECTION 8(5))
====================================================================================================

5.1 Field-Level Encryption (FLE) at Rest (AES-256-GCM)
------------------------------------------------------
All high-risk and critical personal identifiers (Aadhaar, PAN, Bank Account Number, Passport, Health Records) 
must be encrypted before hitting database storage.

Algorithm: AES-256-GCM (Authenticated Encryption with Associated Data).
Payload Structure: `iv:auth_tag:ciphertext` (all base64-encoded).

Node.js Implementation Specification:
```javascript
const crypto = require("crypto");

const ALGORITHM = "aes-256-gcm";
const IV_LENGTH = 12; // 96 bits for GCM
const MASTER_KEY = Buffer.from(process.env.DPDP_MASTER_ENCRYPTION_KEY, "hex"); // 256-bit key

function encryptPII(plainText) {
  if (!plainText) return null;
  const iv = crypto.randomBytes(IV_LENGTH);
  const cipher = crypto.createCipheriv(ALGORITHM, MASTER_KEY, iv);
  
  let encrypted = cipher.update(String(plainText), "utf8", "base64");
  encrypted += cipher.final("base64");
  const authTag = cipher.getAuthTag().toString("base64");

  // Format: iv:authTag:ciphertext
  return `${iv.toString("base64")}:${authTag}:${encrypted}`;
}

function decryptPII(cipherPayload) {
  if (!cipherPayload || typeof cipherPayload !== "string") return null;
  const parts = cipherPayload.split(":");
  if (parts.length !== 3) return cipherPayload; // Fallback if already plaintext

  const [ivB64, tagB64, encryptedB64] = parts;
  const iv = Buffer.from(ivB64, "base64");
  const authTag = Buffer.from(tagB64, "base64");
  
  const decipher = crypto.createDecipheriv(ALGORITHM, MASTER_KEY, iv);
  decipher.setAuthTag(authTag);
  
  let decrypted = decipher.update(encryptedB64, "base64", "utf8");
  decrypted += decipher.final("utf8");
  return decrypted;
}
```

5.2 Blind Indexing (HMAC-SHA256) for Searchable Encrypted Fields
----------------------------------------------------------------
Problem: When an Aadhaar or Phone number is encrypted with AES-256-GCM, the ciphertext is randomized by the IV. 
Therefore, queries like `WHERE phone = ?` will fail.
Solution: Blind Indexing.
- Compute a deterministic, keyed HMAC-SHA256 hash of the normalized plaintext value.
- Store this hash in a separate indexed column (e.g., `phone_blind_idx`).
- To look up a user by phone, compute `HMAC(phone)` and query: `WHERE phone_blind_idx = ?`.

```javascript
const BLIND_INDEX_SALT = process.env.DPDP_BLIND_INDEX_SECRET || "dpdp-search-salt-2026";

function computeBlindIndex(value) {
  if (!value) return null;
  const normalized = String(value).trim().toLowerCase();
  return crypto.createHmac("sha256", BLIND_INDEX_SALT).update(normalized).digest("hex");
}
```

5.3 Role-Based Dynamic Data Masking Middleware
----------------------------------------------
Personal data displayed on screens must be masked unless the user has authorized clearance:
- Aadhaar: `XXXXXXXX1234` (Mask all but last 4 digits)
- Mobile: `XXXXXX7890` (Mask all but last 4 digits)
- PAN: `XXXXX1234X` (Mask initial 5 and final 1 character)
- Email: `a*****r@example.com`

```javascript
function maskAadhaar(val) {
  if (!val || val.length < 4) return "XXXXXXXXXXXX";
  return `XXXXXXXX${val.slice(-4)}`;
}

function maskMobile(val) {
  if (!val || val.length < 4) return "XXXXXXXXXX";
  return `XXXXXX${val.slice(-4)}`;
}

function maskEmail(email) {
  if (!email || !email.includes("@")) return "******@domain.com";
  const [user, domain] = email.split("@");
  return `${user[0]}*****${user[user.length - 1]}@${domain}`;
}
```

8.1 Granular Consent Modal (React Component Pattern)
----------------------------------------------------
```jsx
import React, { useState, useEffect } from "react";
import axios from "axios";

export const DPDPNoticeConsentModal = ({ onConsentComplete, language = "en" }) => {
  const [notice, setNotice] = useState(null);
  const [consents, setConsents] = useState({});

  useEffect(() => {
    axios.get(`/api/dpdp/notice/active?lang=${language}`).then(res => {
      setNotice(res.data);
      // Mandatory purposes pre-selected; optional unselected by default
      const initial = {};
      res.data.purposes.forEach(p => { initial[p.purpose_id] = p.mandatory; });
      setConsents(initial);
    });
  }, [language]);

  const handleSubmit = async () => {
    const granted = Object.keys(consents).filter(k => consents[k]);
    await axios.post("/api/dpdp/consent/record", {
      notice_id: notice.notice_id,
      notice_version: notice.version,
      language,
      granted_purposes: granted
    });
    onConsentComplete();
  };

  if (!notice) return null;

  return (
    <div className="dpdp-modal-backdrop">
      <div className="dpdp-modal-card">
        <h2>{notice.title}</h2>
        <div className="dpdp-notice-body">{notice.body}</div>
        
        <div className="dpdp-purpose-list">
          {notice.purposes.map(p => (
            <label key={p.purpose_id} className="dpdp-checkbox-row">
              <input
                type="checkbox"
                checked={consents[p.purpose_id]}
                disabled={p.mandatory} // Cannot uncheck mandatory core service
                onChange={e => setConsents({...consents, [p.purpose_id]: e.target.checked})}
              />
              <span>{p.name} {p.mandatory && <strong className="required">(Required)</strong>}</span>
            </label>
          ))}
        </div>

        <button onClick={handleSubmit} className="dpdp-submit-btn">
          I Agree & Continue
        </button>
      </div>
    </div>
  );
};
```
